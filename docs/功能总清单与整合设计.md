## 0. 先看结论：真正的病是**同一个硬件有三个写入方**

| 硬件节点 | 谁在写 | 后果 |
| :- | :- | :- |
| `intel_pstate/max_perf_pct` | ① 性能档位 `apply_preset`<br>② UI 的 CPU 滑块<br>③ `omen-thermal` 分级 | **三方无仲裁**，最后写的赢 |
| `intel_pstate/no_turbo` | 同上三方 | 同上 |
| `cpu*/scaling_max_freq` | ① 档位 `apply_preset`<br>② UI 的「频率上限」<br>③ `omen-thermal`（不写，用 pct 代替） | 两方 |
| `energy_performance_preference` | ① 档位 ② UI | 两方 |
| `fan_unthrottle` | ① `omen-thermal`（L2+ 拉满）② CLI `--omen unthrottle` | **与下面那条抢同一个风扇** |
| `fan_speed`（连续曲线） | `omen-fand` / `fan-dynamic.sh` | 与上面那条抢同一个风扇 |

**⇒ 不是功能不够，是功能没有边界。**

## 1. 五层架构（自下而上）

```
┌─ L5 服务层 ─────────────────────────────────────────────────────────┐
│  omen-fand.service   已装/已启用   风扇曲线守护（Rust，用户身份）      │
│  omen-thermal.service  **未装**     分级散热策略（bash，root）        │
└─────────────────────────────────────────────────────────────────────┘
┌─ L4 应用层 ─────────────────────────────────────────────────────────┐
│  omen-control（GTK4 面板，8 个分组）                                │
│  omen-control（CLI：--hud --fan-daemon --check --reset --apply       │
│                --install --omen set/unthrottle）                     │
└─────────────────────────────────────────────────────────────────────┘
┌─ L3 提权层 ─────────────────────────────────────────────────────────┐
│  /usr/libexec/omen-control/omen-control-helper + /etc/sudoers.d/omen-control│
│  8 个子命令：set-maxfan / set-cpu-pct / set-epp / set-turbo          │
│              set-cpu-freq / set-rapl / set-gpu-clk / set-fan-daemon  │
│  （set-governor 已于 2026-10-11 删除：无调用者、omen-thermal 也不存在）│
└─────────────────────────────────────────────────────────────────────┘
┌─ L2 内核公开接口 ───────────────────────────────────────────────────┐
│  intel_pstate（max_perf_pct / no_turbo）  root:root 644  **需提权**  │
│  cpufreq（scaling_max_freq / epp）        root:root 644  **需提权**  │
│  RAPL（constraint_0_power_limit_uw）      root:root 644  **需提权**  │
│  hwmon（coretemp/x86_pkg_temp）           只读                       │
│  omen-wmi（fan_speed / fan_unthrottle）   root:plugdev 664 **免提权**│
└─────────────────────────────────────────────────────────────────────┘
┌─ L1 内核模块 hp-wmi-omen（12 个 sysfs 属性）─────────────────────────┐
│  fan_count(r) fan_rpm(r) fan_unthrottle(rw) **fan_speed(rw)**         │
│  profile_version(r) design_data(r) gpu_modes(rw) performance_mode(rw) │
│  fan_table(r*) probe_all(rw) fan_speed_victus_s(rw,本机不适用)        │
│  ec_byte(0600,root)                                                   │
└─────────────────────────────────────────────────────────────────────┘
```

**权限分界线很关键**：风扇走 `plugdev` 免提权（所以守护能以普通用户跑）；
CPU/GPU 限制是 `root:root`，**必须经 helper**。整合方案必须尊重这条线。

## 3. `omen-thermal` 与 `omen-fand` 的能力差

| | `omen-thermal` | `omen-fand` |
| :- | :- | :- |
| 定位 | **整套策略** | 只调风扇 |
| 进程 | root / 5 秒 | 普通用户 / 2 秒 |
| 温度源 | **包温 + EMA(α=0.35)** | 各核最高 + 三点中位数 |
| 风扇 | `fan_unthrottle` **两态** | `fan_speed` **连续 20~48%** |
| CPU 上限 | ✅ 每级 100/85/75/62/45% | ❌ |
| 睿频 | ✅ L4 关 | ❌ |
| GPU 锁 | ✅ L3+ 1500/1200 MHz | ❌ |
| 分级 | L0–L4 + 迟滞 5°C + 连续 3 次 | 无分级，步进 150 RPM |
| 配置 | `/etc/omen-thermal.conf` | `~/.config/omen-control/config` |

**分级阈值**：CPU 70/76/80/88 °C，GPU 65/68/70/78 °C。
**它自己记录的缺陷**（`omen-thermal/缺陷分析-已安装版本.md`）：GPU 侧零控制、
无自动回路、与守护打架 —— **那是对 10-07 那个版本的批评，10-08 之后都已修正**。

### 4.7 三轮收口（同日，按用户实测反馈）

用户实测报出四个问题，全部有明确根因：

| 现象 | 根因 | 修法 |
| :- | :- | :- |
| **改了曲线不生效** | 编辑器的 `on_changed` 只 `save_config`，**没让守护重载** —— 守护在启动时把曲线读进内存 | 保存后若守护在跑就 `restart_fan_daemon()` |
| **切档位后守护用旧基准** | 守护的 `base_pct` 只在**启动时读一次** | 改为**每轮现读**档位 |
| **限制会放宽档位** | 目标值直接写 `cpu_pct`，没跟档位取 min ⇒ eco(40%) 会被"收紧"到 62% | `target` 加 `base_pct` 参数，只取 `min` |
| **PL1 锁死 55W 不可调** | UI + helper **双层**都拿 `constraint_0_max_power_uw`（读出来 55）当"可写上限"，而实际 PL1 是 **135 W** ⇒ 判为越界后永久禁用 | 范围放宽到 5~200 W、控件始终可调、**写后读回校验**，被钳/被覆盖就明确报出来 |
| **渐进 vs 两段**（用户授权决定） | 两段模型会在一到阈值时从基准直接跳到目标值（突变） | 改成**渐进**：温度每升 5°C 多压一档（共 4 档，跨度 15°C），回落按同样档位反向恢复 |

**渐进的分档设计（关键约束）**：不能做成连续值 —— 那会让守护每 2 秒都得到新目标、
每轮 fork 一次 `sudo helper` 去写 CPU/GPU。分 4 档后一次升温最多写 4 次。

**实测（阈值 80/75，最低 55%/1200MHz，基准 100）**

```
 70°C | 不干预
 80°C | CPU 89% · GPU 1850 MHz
 85°C | CPU 78% · GPU 1525 MHz
 90°C | CPU 66% · GPU 1200 MHz
 95°C | CPU 55% · GPU 1200 MHz   ← 到底
```

**另一个由单测抓出的真 bug**：迟滞只判"是否触发"，没判"值不能回退" ——
温度在两档之间波动时 `ramp` 会算出更大的值 ⇒ 守护会来回写（62% ↔ 90%）。
修法：目标值再与 `prev` 取 `min`，回退的唯一入口是"温度低于触发点 − 迟滞"。

## 5. 整合设计：**一个守护、一份配置、一条仲裁规则**

### 5.1 核心决策

1. **唯一守护 = `omen-fand`（Rust）**
   `omen-thermal`、`fan-dynamic.sh`、`gpu-thermoguard.sh`、`thermoguard.sh` 全部退役。
2. **唯一配置 = `~/.config/omen-control/config`**
   `OMEN_CONFIG_DIR` 已支持（解决 systemd 的 `$HOME` 陷阱）。
3. **职责切分（关键）**：

```
   风扇（连续、细腻）  ← 曲线 curve.<档位>      写 fan_speed  无需提权
   限制（离散、收紧）  ← 阈值 limit.*           经 helper     需提权
```

**两者用各自的通道、由同一个守护、读同一个温度 ⇒ 天生不打架。**
（`omen-thermal` 的问题正是在 L2 就用 `fan_unthrottle` 去抢风扇 —— 那条路不用了。）

### 5.2 分层语义：档位是"基准"，限制是"收紧"

```
        用户选的档位（性能档位）           ← 基准：CPU 上限 / EPP / 睿频 / 频率墙
                 ↓  在这个基准之上
        按温度自动收紧（限制等级）          ← 只做"更保守"的调整，绝不放开
                 ↓
        风扇曲线                            ← 独立通道，连续
```

**好处**：档位仍是用户主动选择；温度高时只在基准上再收紧；
高负载结束自动恢复基准 —— 不需要"退出守护才还原"。

### 5.3 配置形态（**已实现**，与 `curve.*` 同风格）

```
preset=balanced                 # 基准（已有）
curve.balanced=60:2200,72:3200,82:4597      # 风扇（已有）

# 限制策略：**两个温度上限**（GUI 里就是两个数字输入）
limit.enabled=1
limit.cpu_temp=80       # CPU 达到 80°C → 上限收紧（可设 50~100，步幅 5）
limit.cpu_pct=62        # 收紧到 62%
limit.gpu_temp=75       # GPU 达到 75°C → 锁 SM 时钟（可设 50~90，步幅 5）
limit.gpu_mhz=1200      # 锁到 1200 MHz
limit.cool_down=4       # 低于「触发点 − 它」才回退（迟滞）
limit.confirm=3         # 连续 N 次同向才写硬件（防抖）
```

**呈现给用户的就是两个数字**：CPU 到多少度开始压、GPU 到多少度开始锁。

**风扇完全不受影响**：本策略只写 `intel_pstate` 与 `nvidia-smi`，
风扇唯一来源仍是曲线（用户明确要求：「当前的风扇策略已经够用了」）。
守护里原先那条「临界温度 95°C 无条件拉满风扇」的兜底**已删除** ——
它是当年没有压热源手段时的迫不得已，而且曲线末点本来就是 4597 RPM，属于冗余。
