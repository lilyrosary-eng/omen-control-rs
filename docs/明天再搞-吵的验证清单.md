## 优先级 1：把 PL1 的阈值定下来（**最要紧**）

### 背景（为什么这条排第一）

你报的「守护容易冲顶」根因已经查清 —— **CPU 温度是毫秒级跳变的，风扇追不上**：

```
守护日志实测（10-11 00:22）
00:22:24 → 写 46%（4597 RPM） CPU 81°C（原始 96）
00:22:31 → 写 23%            CPU 60°C
00:22:35 → 写 46%（4597）     CPU 83°C     ← 4 秒内又冲顶
00:22:53 → 写 46%（4597）     CPU 94°C（原始 96）
```

i9-12900HX（16 核 / PL1 135 W）睿频一上来就能在 2 秒内把某个核从 60°C 推到 96°C，
而风扇有 ~26 秒软启动惯性 ⇒ **纯靠调转速必然反复冲顶**。

**从源头压热源才是解法** —— 你 Windows 侧限 30 W / 40 W 就是这个思路，是对的。

### 已完成的（这部分不用再做）

- ✅ PL1 **可写且不会被系统服务改回**（实测：90 W 在 8 线程负载、pkg 93°C 下 50 秒纹丝不动）
- ✅ 新配置项 `limit.cpu_w=45` —— 达到 `limit.cpu_temp` 就把封装功耗收到这个值
- ✅ 与 `limit.cpu_pct`（百分比）**独立**：想纯限功耗就设 `cpu_pct=100` + `cpu_w=45`
- ✅ 功耗墙**不分档**（硬墙，一触发就到目标值），温度回落 + 迟滞后还原
- ✅ 36 个单测通过（含 3 个 PL1 专用）
- ✅ UI 已加「CPU 功耗墙（PL1）」输入（高温限制组内，范围 5~200，步幅 5）

### ⏳ 明天要做的：**45 W 是我估的，得实测**

```bash
# ① 先手动试几个值，看哪个能压住温度又不至于太慢
sudo /usr/libexec/omen-control/omen-control-helper set-rapl 45
#   然后正常用一会儿（开浏览器/编译/看视频），观察：
#     - CPU 温度峰值（是否还到 90+）
#     - 体感有没有明显变慢

# ② 换值再试（你觉得热就往下调，觉得慢就往上调）
sudo /usr/libexec/omen-control/omen-control-helper set-rapl 35   # 更凉更慢
sudo /usr/libexec/omen-control/omen-control-helper set-rapl 55   # 更快更热

# ③ 看当前值 / 还原
cat /sys/class/powercap/intel-rapl:0/constraint_0_power_limit_uw
sudo /usr/libexec/omen-control/omen-control-helper set-rapl 135  # 还原出厂
```

**判据**：找一个"温度峰值不再冲 90°C，且日常使用无明显卡顿"的值，填进 `limit.cpu_w`。

> 你 Windows 侧的 30/40 W 可以作为起点 —— **建议先试 40 W**。

## 优先级 5：ppd 决策（**需要你拍板**）

`power-profiles-daemon` 与我们的性能档位**都写 EPP**（能效偏好），会互相覆盖。

| 选项 | 做法 | 代价 |
| :- | :- | :- |
| **A（我推荐）** | `sudo systemctl disable --now power-profiles-daemon` | 失去 GNOME 电源模式菜单；我们的四档是它的超集 |
| B | 保留 ppd，档位不写 EPP | 省电/安静档效果打折 |
| C | 现状共存 | EPP 归属不确定 |

> 顺便：**PL1 与 ppd 无关**（已实测 ppd 不写 RAPL），所以这条不影响功耗墙。
