## ① PL1 冲突：实测证明**不存在**

### 实验（本机，唯一一次真正的写入实验）

```
① 写 PL1 = 90 W（经 helper，自带读回校验）
   → helper 返回成功；MSR 读回 90 W，MMIO 读回 90 W

② 8 线程 CPU 负载，持续 50 秒，pkg 温度冲到 93°C
   +5s  PL1=90  +10s PL1=90  +15s PL1=90  +20s PL1=90  +25s PL1=90
   +30s PL1=90  +35s PL1=90  +40s PL1=90  +45s PL1=90  +50s PL1=90
   ⇒ 全程纹丝不动

③ 还原 135 W ✅
```

### 为什么 thermald 动不了它

`thermald` 的 `thermal-cpu-cdev-order.xml` 里确实写了：

```xml
<CoolingDevice>rapl_controller</CoolingDevice>
```

**但本机内核没有注册这个 cooling device** —— `/sys/class/thermal/cooling_device*` 实际只有
`Processor`×24 + `intel_powerclamp`×1。设备不存在 ⇒ thermald 想用也用不上。

### 为什么 ppd 不动它

`power-profiles-daemon` 0.30 管的是**平台档位与能效偏好**，不是功耗墙。
它的二进制里能找到 `energy_performance_preference` / `intel_pstate` / `acpi_platform_profile`，
**没有 RAPL / power_limit 相关符号**。

### 结论

**不用消 —— 没有这个冲突。** 上一轮我说的"两者都在运行、可能把 PL1 改回去"是**过度推测**，
实测已经证伪。可以作为已知事实记录：**PL1 写下去就是你的，不会被系统服务改回。**

> ⚠ 唯一保留的防御：helper 仍做**写后读回校验**。这不是因为预判有冲突，
> 而是"不确定能不能写时，写一次看结果"比"预先禁用控件"好（见下一节的血案）。

## ② 但确实有一处真交叉点：**ppd ⇄ 性能档位（EPP）**

| 节点 | ppd 会写吗 | thermald 会写吗 | 我们的代码会写吗 |
| :- | :- | :- | :- |
| **PL1（RAPL）** | ❌ | ❌（设备未注册） | ✅ 手动 + 限制策略 |
| **EPP** | ✅ **会**（二进制含 `energy_performance_preference`）| ❌ | ✅ **性能档位**（`set_epp`） |
| **platform_profile** | ✅ 会 | ❌ | ❌ 不碰 |
| `max_perf_pct` / `scaling_max_freq` / `no_turbo` | ❌ | ❌ | ✅ 档位 + CPU 组 + 限制策略 |
| `fan_speed` / `fan_unthrottle` | ❌ | ❌ | ✅ 曲线（唯一来源）|

**⇒ `EPP` 有两个写入方：ppd 与我们的性能档位。**

ppd 会在**切换 profile、resume 等时机**重新应用它的偏好。你切到"省电"档（EPP=`power`）之后，
ppd 若重新应用 `performance` profile，会把 EPP 改回 `performance` —— 表现就是"省电档好像没生效"。

### 三个选项（需要你决策）

| 选项 | 做法 | 代价 |
| :- | :- | :- |
| **A. 关掉 ppd**（推荐）| `systemctl disable --now power-profiles-daemon` | 失去 ppd 的图形化 profile 切换（GNOME 电源模式菜单）。但**我们的性能档位就是它的超集**（4 档 vs 3 档）|
| **B. 保留 ppd，档位不写 EPP** | 从 `apply_preset` 移除 `set_epp` | 省电/安静档失去 EPP 这一维（只剩 CPU 上限 + 频率墙），效果打折 |
| **C. 现状共存** | 什么都不做 | EPP 归属不确定；档位的 EPP 可能随时被 ppd 覆盖 |

**我倾向 A**，理由是这正是你说的"整合"：
`power-profiles-daemon` 与本项目的性能档位是**功能完全重叠的两个实现**（都管 EPP + platform_profile），
同时留着就必然互相覆盖。而 ppd 的 profile 切换在 GNOME 里很少用（大多数人设一次就不动）。

## ③ CPU/GPU"不可调"：**部署链断裂**（本轮最主要的发现）

### 现象

用户报告"现在 CPU 和 GPU 都是不可调的状态"。

### 根因：桌面启动器指向一个 2 天前的旧二进制

```
桌面启动器  ~/.local/share/applications/omen-control.desktop
            Exec=/home/<user>/.local/bin/omen-control     ← 893 KB · 2026-10-09 21:35

新二进制    target/debug/omen-control                      ← 71 MB · 2026-10-11 00:17
服务用的    /usr/local/bin/omen-control                    ← 71 MB · 2026-10-11 00:20

而 install-fand.sh 只装 /usr/local/bin，完全不碰 ~/.local/bin 与 .desktop。
```

### 旧版缺什么（用 `grep -ac` 数二进制里的字符串）

| 文案 / 配置键 | 旧版（10-09） | 新版（10-11） |
| :- | :- | :- |
| 「高温时自动压 CPU/GPU」 | **0** | 3 |
| 「自动风扇控制」 | **0** | 3 |
| 「自动散热」（已删除的分组）| **5** | 0 |
| `limit.enabled`（配置键）| **0** | ✅ |
| `curve.performance`（配置键）| **0** | ✅ |

**⇒ 旧版根本不认识 `curve.*` / `limit.*` 配置键** ⇒ 曲线与限制统统不显示。
用户看到的"CPU/GPU 不可调"，就是这个旧版本。

### 修复（本轮完成）

`install-fand.sh` 现在一次性部署**两处** + 修正桌面启动器：

```bash
hdr "② 安装二进制"
install -m 0755 "$bin" "$BINDIR/omen-control"                    # /usr/local/bin（服务）
install -d -m 0755 -o "$u" -g "$u" "$_home/.local/bin"           # 用户级
install -m 0755 "$bin" "$_home/.local/bin/omen-control"          # 桌面启动器用
ensure_desktop "$u" "$_home"                                     # Exec/Name/Comment 自动对齐
```

`ensure_desktop()` 已用替身验证三个场景：Exec 正确但文案旧 → 修正文案；
Exec 指向别处 → 改回来；.desktop 缺失 → 创建。

> **通用教训（已写进技能）**：`"程序能跑" ≠ "跑的是最新版"`。
> 只要存在"开发目录二进制"与"安装位置二进制"的副本，就必须有一个**单向的部署动作**把它们对齐，
> 并且部署前**核对版本**（mtime / 字符串 / `--version`）。否则症状是"新功能完全不出现"，且**零报错**。

## ④ 完成度（分层给出，避免一个笼统的百分比骗人）

| 层 | 完成度 | 依据 |
| :- | :- | :- |
| **风扇控制（核心能力）** | **100%** | 20~48% ⇒ 1992~4950 RPM 连续可编程；两风扇独立寻址；与温度解耦；停转保护；交回可靠 |
| **温度限制（压热源）** | **功能 100% / 标定 0%** | 渐进 4 档已实现并单测通过；但阈值 `80→62%` / `75→1200MHz` 仍是估值，`limit-bench.sh` 未跑 |
| **性能档位 / CPU / GPU** | **95%** | 四档 + PL1（实测可写）+ 频率墙 + GPU 时钟锁；GPU 功耗墙本机 vBIOS 实测空操作 |
| **GUI** | **90%** | 曲线编辑器（拖点/增删/实时 RPM）、遮罩、Toast、四档切换；缺：曲线导入导出、诊断面板 |
| **服务化 / 部署** | **80%** | systemd 服务 + Restart + ExecStopPost 兜底；部署链本轮修完；**尚无 release 一键安装** |
| **测试** | **70%** | 33 个单测（curve 10 / limit 19 / ui 1 / 其它 3）；**缺**：端到端集成测试、长时间稳定性 |
| **文档** | **85%** | 4 份文档共 855 行（通道清单、功能总清单与整合设计、本评估、脚本地图）|

**综合：功能层 ~90%，可交付性 ~85%。**
**瓶颈不在功能，在"部署 + 验证"这两个工程环节。**

### 还不能算"完成"的三件事

| 项 | 为什么重要 | 成本 |
| :- | :- | :- |

## ⑤ 这台机器"做不到"的部分（不变）

| 层 | 状况 | 依据 |
| :- | :- | :- |
| EC 固件的风扇曲线表 | **在 ROM 里**，运行时改不到 | 设定值在 EC MMIO（`0xFE400000+0x53F/0x8CC`），控制环读自己的 ROM 表 |
| BIOS 风扇/热设置 | 通道**开着**，本机 SKU **不提供** | `hp-bioscfg` 只暴露 3 个属性且全 `-r--r--r--` |
| 标准 ACPI 风扇接口 | **不存在** | 368 个 ACPI 设备里没有 `PNP0C0B` |
| 内核热框架调风扇 | **掐不到** | 30 个 cooling device 里**无 Fan 型** |
| 转速超 ~4950 | **48% 以上是饱和死区** | 50% 与 100% 实测都是 ~4950 |
| GPU 功耗墙（`-pl`）| 本机 vBIOS **空操作** | 写入返回成功但读数不变；`-lgc` 时钟锁是唯一有效手段 |

## ⑥ 风险点（更新）

| 风险 | 现状 | 缓解 |
| :- | :- | :- |
| **部署副本不一致** | ⚠ 本轮踩到（GUI 停在 2 天前的构建）| `install-fand.sh` 现在装两处 + 对齐 .desktop |
| daemon 被 `SIGKILL` | 手动值会留在 EC | **无解**（不可捕获）；`echo 0 > fan_speed` 手动救 |
| 直接关终端窗口 | 已修 | Rust daemon 注册 SIGINT/SIGTERM/SIGHUP |
| 配置文件损坏 | 解析失败 ⇒ 空曲线 = 不接管 | 安全降级 |
| 风扇停转/失控 | 接管中 <600 或 >5400 连续 3 次 ⇒ 交回并退出 | 已实现 |
| 传感器错读 | EC 偶发返回"上一个偏移"；包温瞬时冲 93~100°C | 三点中位数 + 连续 N 次判据 |
| **ppd 覆盖 EPP** | ⚠ 未处理 | 见 ② 的三个选项 |
| `thermald` 与 `intel_powerclamp` | 它可能注入 idle 周期来降温 | 未测；如需排除可 `systemctl disable thermald` |

> **已删除的风险**（上一版列过，现已消除）："超温 ≥95°C 无条件满速，独立于曲线" ——
> 那条**绕过用户的曲线策略**；用户明确要求删除（既然有了压热源的手段，且曲线末点本身就是满速）。

## ⑦ 建议的下一步顺序

| 优先级 | 做什么 | 为什么 |
| :- | :- | :- |
| **1** | **装**（`install-fand.sh install`）| 部署链已修好；不装就没有服务化，也没法验证 |
| **2** | **决定 ppd 怎么处理**（选 A / B / C）| 这是唯一剩下的"多写入方"问题 |
| **3** | **跑 `limit-bench.sh cpu`** 定阈值 | 让温度限制从"估的"变成"量过的" |
| **4** | 过夜稳定性验证 | 决定能不能"放着不管" |
| 5 | （可选）温度源换成 package / EMA | 更贴近固件行为；会改变现有曲线的响应，需重校 |

## 关于"完全掌控"

**做不到，而且不该以此为目标。** 更实际的目标是：

> **在机器开放的范围内做满，并且让"做不到的部分"有明确、安全的默认行为。**

风扇曲线我们做满了（连续可编程）；EC ROM 碰不到 —— 但 BIOS 曲线本身就是安全兜底
（daemon 一挂，写 0 就交回它）。这个"安全降级"，比"强行去碰 ROM"更值得投入。
